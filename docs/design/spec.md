# voice-to-doc — спецификация

Дата: 2026-10-12 · Статус: на согласовании

## 1. Цель

Локальный инструмент: загружаешь запись интервью или лекции → получаешь структурированный документ (выжимка + почти дословный текст по разделам с таймкодами; для интервью — реплики с подписями). Скачивается в Markdown и Word.

**Критерий успеха:** часовая лекция/интервью на русском → готовый документ быстрее чем за 15 минут, читается без правки.

### Исходные условия
- Пользователь один, работает на своём ноутбуке (Intel Core i3, 8 ГБ ОЗУ) — тяжёлые модели локально не запускаем.
- Бесплатно: только бесплатный тариф Groq. Отправка записей в Groq допустима.
- Интерфейс — веб-страница в браузере, сервер запускается локально.

### Допущения (согласованы)
- Язык записей — русский; длина до ~2 часов; форматы mp3, m4a, ogg, wav, а также видео (mp4 и др.).
- Входа, аккаунтов и общего доступа нет.

### Вне рамок (YAGNI)
Редактирование текста на странице, переименование спикеров, поиск и удаление записей через UI, разметка спикеров по голосу (диаризация), более двух ролей в интервью, мультиязычность в интерфейсе.

## 2. Внешние ограничения (Groq, бесплатный тариф)

Источник: console.groq.com/docs/rate-limits (проверено 2026-10-12; точные значения — на странице лимитов аккаунта).

| Модель | Лимиты |
|---|---|
| `whisper-large-v3` | 20 запросов/мин, 2000/день, 7200 аудиосекунд/час, 28 800 аудиосекунд/день; файл ≤ 25 МБ |
| `openai/gpt-oss-120b` | 30 запросов/мин, 1000/день, 8 000 токенов/мин, 200 000 токенов/день |

Следствие: оформление идёт блоками ~1 блок/мин; ≈ 3–4 часа записей в день упираются в дневной лимит токенов.

Все значения лимитов и имена моделей — в настройках (`.env`), не в коде.

## 3. Архитектура

Python-приложение (FastAPI + uvicorn), одна HTML-страница с ванильным JS. Проект: `~/Projects/voice-to-doc`.

```
voice_to_doc/
  config.py      настройки из .env (ключ, модели, лимиты, размеры блоков)
  audio.py       ffmpeg: перекодирование и нарезка
  transcribe.py  распознавание через Groq Whisper
  structure.py   оформление текста через LLM
  ratelimit.py   учёт токенов/запросов в минуту
  render.py      Markdown и .docx
  jobs.py        задания: состояние, очередь, возобновление
  groq_client.py тонкая обёртка над Groq SDK (подменяется в тестах)
  app.py         FastAPI: API + раздача страницы
  static/        index.html, app.js, style.css
data/<job_id>/   файлы задания
tests/
```

Каждый модуль имеет одну задачу и тестируется отдельно. Сетевые вызовы — только через `groq_client.py`, остальные модули получают клиент параметром.

### 3.1 Конвейер задания

Шаги выполняются строго по порядку; результат каждого шага сохраняется на диск, поэтому задание возобновляется с первого незавершённого шага.

1. **prepare** (`audio.py`) — ffmpeg (бинарник из пакета `imageio-ffmpeg`) перекодирует исходник в моно, 16 кГц, низкий битрейт (ogg/opus ~32 кбит/с) и режет на куски по 600 с. Результат: `chunks/000.ogg …` + `chunks.json` (смещение начала каждого куска в секундах, длительность записи).
2. **transcribe** (`transcribe.py`) — каждый кусок → Whisper (`language=ru`, `response_format=verbose_json`). Таймкоды сегментов сдвигаются на смещение куска. Результат по кускам: `transcript/000.json …`; после всех кусков — `transcript.json`: список сегментов `{start, end, text}` (секунды от начала записи). Уже распознанные куски повторно не отправляются.
3. **structure** (`structure.py`) — см. 3.2. Результат по блокам: `blocks/000.json …`; затем `document.json`.
4. **summary** — один запрос: на входе заголовки разделов и 1–2 первых предложения каждого (для интервью — первые реплики по ходу разговора), на выходе `{title, summary: [3–7 пунктов]}`. Записывается в `document.json`.
5. **render** (`render.py`) — `document.json` → `result.md` и `result.docx`.

### 3.2 Оформление текста

**Нарезка на блоки.** Сегменты упаковываются по порядку в блоки бюджетом ≈ 2 500 токенов входа (оценка токенов — по числу символов, коэффициент в настройках). Сегмент не разрезается. В промпте каждый сегмент — строка `[MM:SS] текст` (для записей ≥ 1 ч — `[H:MM:SS]`).

**Режимы и формат ответа (JSON, `response_format=json_object`):**
- Лекция: `{"continues_previous": bool, "sections": [{"title": str, "start": "MM:SS", "paragraphs": [str]}]}`
- Интервью: `{"utterances": [{"speaker": "Интервьюер"|"Собеседник", "start": "MM:SS", "text": str}]}`

**Правила промпта:** не пересказывать и не сокращать по смыслу; разрешено только убирать слова-паразиты, повторы, оговорки, расставлять пунктуацию и делить на абзацы; таймкоды брать только из входных строк.

**Связность:** в запрос для блока N добавляется контекст блока N−1: заголовок последнего раздела (лекция) или две последние реплики с ролями (интервью). Лекция: если `continues_previous=true`, первый раздел блока склеивается с последним разделом предыдущего (его заголовок отбрасывается).

**Проверки ответа:**
- JSON не разбирается или не соответствует схеме → 1 повтор; затем запасной вариант.
- Таймкод, которого нет во входе → заменяется ближайшим входным по времени.
- Длина очищенного текста < 70 % длины входного текста (по символам) → 1 повтор со строгой инструкцией; затем запасной вариант.
- Запасной вариант: блок попадает в документ как сырой текст сегментов одним разделом «Не оформлено [MM:SS]» (для интервью — одна реплика без роли) с пометкой.

**Модель документа (`document.json`):** `{title, summary, kind: "lecture"|"interview", duration_s, sections | utterances, warnings: [str]}`.

### 3.3 Лимиты (`ratelimit.py`)

- Скользящее окно 60 с: учитываются запросы и оценка токенов (вход + `max_tokens` ответа). Перед запросом, если лимит в минуту будет превышен, — ожидание до освобождения окна.
- Ответ 429: ожидание по заголовку `retry-after` (если нет — 30 с), повтор без ограничения числа попыток для минутных лимитов.
- Если сообщение 429 указывает на дневной лимит (токенов/запросов/аудиосекунд за день) → `DailyLimitExceeded` → задание в статус `paused`, причина «Дневной лимит Groq исчерпан».
- Часы и `sleep` передаются параметрами — для тестов подставляются фиктивные.

### 3.4 Задания (`jobs.py`)

- Состояние задания — `data/<job_id>/job.json`: `{id, filename, kind, created_at, duration_s, status, step, progress: {done, total}, message}`.
- Статусы: `queued → running → done`; из `running` возможны `paused` (дневной лимит, сеть, неверный ключ, перезапуск программы) и `error` (неисправимо: файл не читается).
- `paused` и `error` возобновляются действием пользователя («Продолжить»/«Повторить»); выполнение начинается с первого незавершённого шага.
- Один фоновый рабочий поток, очередь FIFO: в каждый момент выполняется одно задание.
- При старте приложения задания в статусе `running` переводятся в `paused` («Работа прервана перезапуском»).
- «Переоформить» (`restructure`, можно сменить `kind`): удаляет `blocks/`, `document.json`, `result.*` и ставит задание в очередь с шага structure.
- Журнал — `data/<job_id>/log.txt` (шаги, повторы, ожидания, ошибки; без ключа API).

### 3.5 Ошибки

| Ситуация | Реакция |
|---|---|
| ffmpeg не смог прочитать файл | `error`: «Не удалось прочитать файл — это точно аудио или видео?» |
| 401 от Groq | `paused`: «Ключ Groq не подходит», на странице поле для нового ключа |
| Сеть недоступна / 5xx | до 3 повторов (2, 4, 8 с), затем `paused`: «Нет связи с Groq» |
| 429 минутный | ожидание и продолжение (см. 3.3) |
| 429 дневной | `paused`: «Дневной лимит Groq исчерпан» |
| Битый ответ модели | см. 3.2 |
| Загрузка > 2 ГБ | отказ при загрузке с сообщением |

## 4. API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/` | страница |
| GET | `/api/settings` | `{has_key: bool}` |
| POST | `/api/settings` | `{groq_api_key}` → запись в `.env` |
| POST | `/api/jobs` | multipart: `file`, `kind` → `{id}` |
| GET | `/api/jobs` | список заданий (новые сверху) |
| GET | `/api/jobs/{id}` | состояние задания |
| POST | `/api/jobs/{id}/resume` | продолжить `paused`/`error` |
| POST | `/api/jobs/{id}/restructure` | `{kind}` → переоформить |
| GET | `/api/jobs/{id}/result.md` | Markdown (для показа и скачивания) |
| GET | `/api/jobs/{id}/result.docx` | Word |

Сервер слушает только `127.0.0.1`.

## 5. Интерфейс

Одна страница, два состояния (главный экран и экран записи), переключение без перезагрузки.

- **Главный экран:** зона перетаскивания файла, выбор «Лекция / Интервью», кнопка «Расшифровать»; список «Недавние»: имя файла, дата, длительность, статус.
- **Экран записи:** шаги (Подготовка звука, Распознавание N из M кусков, Оформление N из M блоков с оценкой оставшегося времени, Выжимка) и полоса прогресса; опрос состояния раз в 2 с. По готовности — кнопки «Скачать .docx», «Скачать .md», «Копировать», «Переоформить» (с выбором типа) и сам документ (Markdown → HTML на клиенте, библиотека `marked` с cdnjs, пинованная версия; запасной вариант без сети — показ как текст). При `paused`/`error` — сообщение и кнопка «Продолжить»/«Повторить».
- **Нет ключа:** вместо формы загрузки — короткая инструкция, как получить бесплатный ключ на console.groq.com, и поле для него.
- **Стиль:** нейтральная серая палитра, один акцентный цвет; системный шрифт; ширина текста документа ≤ 760 px; светлая/тёмная тема по системе; без градиентов и эмодзи; на ширине телефона без горизонтальной прокрутки.

## 6. Формат документа

```
# <название>
## Кратко
- пункт …
## [00:00] <раздел>          (лекция)
абзацы…
**Интервьюер [03:10]:** …   (интервью)
**Собеседник [03:15]:** …
```

В .docx — та же структура: заголовки уровней 1–2, маркированный список, абзацы; роли в интервью — полужирным. Предупреждения (`warnings`, например «блок не оформлен») — в конце документа.

## 7. Тестирование

- **Модульные (pytest, TDD):** смещения таймкодов кусков; упаковка сегментов в блоки; формат таймкодов; проверка и исправление таймкодов; проверка длины; разбор/валидация JSON; склейка `continues_previous`; запасной вариант; ограничитель (фиктивные часы); распознавание дневного 429; переходы статусов, возобновление с незавершённого шага, перевод `running → paused` при старте; Markdown и .docx (содержимое .docx читается обратно через python-docx).
- **API:** FastAPI TestClient с поддельным Groq-клиентом — полный путь от загрузки до `result.md`.
- **Интеграционный (вручную, с реальным ключом, помечен `@pytest.mark.live`):** 1–2 минуты русской речи, сгенерированной `say -v Milena` по известному тексту; проверяется, что документ создан и содержит ключевые слова исходного текста.
- **UI:** Playwright — загрузка файла, отображение прогресса, результат, скачивание; скриншоты в светлой и тёмной теме, на десктопе и узком экране.
- **Приёмка (пользователь):** реальная запись ~1 ч → документ < 15 мин, читается без правки.

## 8. Окружение и запуск

- Python 3.14, виртуальное окружение `.venv` в проекте; зависимости: fastapi, uvicorn, python-multipart, groq, python-docx, imageio-ffmpeg, python-dotenv; для разработки — pytest, playwright.
- Запуск: `./run.sh` — поднимает сервер на `127.0.0.1:8000` и открывает браузер.
- `.env` и `data/` — в `.gitignore`.

## 9. Изменения после реализации

Что в итоговой версии отличается от исходной спецификации и почему:

- **Модель данных.** Разделы и реплики хранятся в одном поле `items` (тип определяется `kind`), таймкоды — в секундах.
- **Рендерер Markdown** лежит в проекте (`static/vendor`, целостность сверена с npm), а не грузится с CDN: так страница работает без сторонних скриптов и под строгой CSP.
- **Безопасность** (по итогам независимого аудита): проверка `Host` и `Origin`, CSP и защитные заголовки, белый список форматов для ffmpeg (без плейлистов), лимиты 2 ГБ / 6 ч и таймаут ffmpeg, `.env` и `data/` доступны только владельцу, удаление управляющих символов из ответов модели.
- **Удаление записей** (изначально вне рамок) добавлено: расшифровки интервью — личные данные, пользователь должен иметь возможность их стереть.
- **Бюджет токенов.** Размер ответа модели бронируется по размеру блока, а не фиксированно; коэффициент «символов на токен» замерен на реальном API (≈3,8) и выставлен в 3,5.
- **Диск.** Нарезанные куски звука удаляются сразу после распознавания.
